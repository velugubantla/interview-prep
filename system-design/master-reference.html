What is actually graded the bar moves with level

Four signals, roughly equally weighted. Most rejections are on scoping and tradeoff articulation, not on the design itself.

L5
Graded on coverage
  • Remembered to cache, shard, queue
  • Design is complete and correct
  • Answers the question asked
L6
Graded on depth and tradeoffs
  • Two or three levels below any box
  • Names the alternative unprompted
  • Holds a position under pushback
  • Knows failure modes, not just patterns
L7
Graded on problem framing
  • Challenges the requirement itself
  • Discusses org and ownership boundaries
  • Asks what exists today and how we migrate
  • Build vs buy, and who operates it

Silent killers: designing before scoping · never stating a number · one-way monologue · no failure discussion · defending a choice by naming a company that uses it · over-engineering a problem that does not need it.

Opening script

"Let me make sure I'm solving the right problem. I'll assume we're building X for Y users, with A, B, C in scope and D, E out. On non-functionals I'm going to prioritize [availability over consistency] — does that match what you want me to optimize? Let me put some numbers on it before I draw anything."

When you don't know something: "I don't have deep hands-on with X. What I'd reason from first principles is… and the thing I'd want to validate before committing is…" This scores better than bluffing. Bluffing at L6+ is an automatic no-hire when caught.

06 · ACID in full belongs to the main design round

A
Atomicity
All operations commit or none do. Not about concurrency — about abort handling and partial failure.
undo log, rollback
C
Consistency
Application invariants hold before and after. The weakest letter — it is your code's job, not the database's.
constraints, your code
I
Isolation
Concurrent transactions behave as if serial. In practice you get a weaker level, and that level is a design decision.
locks, MVCC, SSI
D
Durability
Once committed, survives crash. On one node that means fsync; in a replicated system it means committed to a quorum.
WAL, fsync, quorum

✓ prevented   ✗ still possible. Level names are not portable — Oracle's "serializable" is snapshot isolation, and MySQL's repeatable read blocks some phantoms. Saying that out loud is a senior signal. Write skew is the one that bites real systems: two transactions each read a valid state, each write, and together break an invariant neither violated alone. It is why double-booking, overdraft and on-call gap bugs survive code review.

07 · SOLID learn the failure mode, not the acronym

S
Single responsibility
One reason to change — meaning one actor who can demand a change to it.
When violatedEvery feature touches the same class. Merge conflicts, wide blast radius, no safe refactor.
O
Open / closed
New behavior arrives as new code, not edits to old code.
When violatedAdding one case means editing a switch in five files, and you will miss one.
L
Liskov substitution
Any subtype is usable wherever the base type is expected, without the caller knowing.
When violatedinstanceof checks scattered through callers. The abstraction is a lie and everyone works around it.
I
Interface segregation
No client forced to depend on methods it does not use. Many small interfaces beat one large one.
When violatedFat interfaces and stubs that throw UnsupportedOperation.
D
Dependency inversion
High-level policy depends on abstractions. Wire concretes in at the edge.
When violatedBusiness logic pinned to a vendor SDK. Untestable, and unmigratable when terms change.
The senior move

Knowing when not to apply these. Every one buys flexibility with indirection, and indirection has a permanent readability cost. An interface for a thing with one implementation and no plausible second is not good design — it is speculative generality. Say the tradeoff out loud: "I'd keep this concrete until there's a second implementation."

08 · Design patterns that actually appear green tag = high frequency · amber card = trap, expect a follow-up

Creational
Factory / Abstract factoryhigh
Object choice depends on runtime input or config. Parsers, payment providers, notification channels.
Builderhigh
Many optional parameters, or an immutable object assembled in steps. Kills telescoping constructors.
Singletontrap
Asked deliberately. Say it is global mutable state, hostile to testing and concurrency — prefer one instance managed by DI.
Prototypelow
Cloning an expensive-to-construct object. Rare in interviews.
Structural
Adapterhigh
Wrapping a third-party or legacy interface so your core does not depend on it. The practical face of dependency inversion.
Decoratorhigh
Layering behavior without subclass explosion. Retries, caching, logging, auth around a client.
Facademedium
One simple entry point over a messy subsystem.
Proxymedium
Lazy loading, access control, or a remote call behind a local-looking interface.
Compositemedium
Trees where leaves and branches are treated uniformly. File systems, org charts.
Flyweightlow
Millions of near-identical objects sharing intrinsic state. Chess pieces, game tiles.
Behavioral
Strategyhigh
Interchangeable algorithms picked at runtime. Pricing, eviction policies, matching. The most common correct answer in LLD.
Observerhigh
One-to-many notification within a process. In-process cousin of pub/sub.
Statehigh
Behavior changes with lifecycle stage. Orders, vending machines, elevators, reservations.
Commandmedium
Operations as objects — undo/redo, queueing, audit log, replay.
Chain of responsibilitymedium
Request passed along handlers until one takes it. Middleware, validation, approvals.
Template methodmedium
Fixed skeleton, variable steps. Prefer composition where you can.

The LLD round framework

01
Clarify scope
Which use cases are in, which are explicitly out.
02
Actors and use cases
Actors and the operations each performs. This produces your interfaces.
03
Core entities
Nouns become classes, verbs become methods. Name the invariants each owns.
04
Relationships
Composition over inheritance. Class diagram with cardinalities.
05
Concurrency
What is shared, locked, immutable. Most-skipped step, easiest differentiator.
06
Extension
"Now add feature X." Good designs absorb it with new classes, not edits.

12 · Twenty minutes before the round

  1. Scope before you design. Get explicit agreement.
  2. Say a number in the first eight minutes.
  3. Draw the happy path end to end before optimizing anything.
  4. Name the alternative and why you rejected it — before being asked.
  5. Offer the deep dive: "the two risky parts are X and Y — which?"
  6. Say what breaks first and how you would detect it.
  7. Say "I don't know," then reason from first principles.
  8. Stop talking. Check in. It is a collaboration, not a lecture.
  9. Don't over-engineer. "One primary is fine here" is a strong-hire sentence.
  10. Close by recapping the two or three decisions that defined the design.
