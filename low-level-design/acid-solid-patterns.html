Companion sheet / low-level design round

ACID, SOLID and design patterns

The material that sits below the distributed system design round. Sized to its real weight in your loop — this is a supporting document, not a second syllabus.

Calibrate before you invest. At L6/L7 nobody will ask you to recite SOLID. What gets tested is whether your reasoning about class and module boundaries is disciplined when an interviewer says "now show me how you'd structure the service internals." Study these for the reasoning, not the acronym. Budget one to two weeks total, in the final phase of your prep.

ACID and isolation levels — these belong to the system design round, not this one.

ACID in full the only item here that belongs in the main design round

A
Atomicity
All operations in a transaction commit, or none do. Not about concurrency — about abort handling and partial failure.
Enforced by: undo log, rollback
C
Consistency
The application's invariants hold before and after. The weakest letter — it is the app's job, not the database's, and Kleppmann calls it the odd one out.
Enforced by: constraints, your code
I
Isolation
Concurrent transactions behave as if serial. In practice you get a weaker level, and the level you get is a design decision.
Enforced by: locks, MVCC, SSI
D
Durability
Once committed, survives crash. On a single node that means fsync to disk; in a replicated system it means committed to a quorum.
Enforced by: WAL, fsync, quorum

The interview-relevant part is this matrix. If you can produce it under pressure and say which anomaly your design tolerates, that is a strong signal on its own.

✓ prevented   ✗ still possible. Level names are not portable across engines — Oracle's "serializable" is snapshot isolation, and MySQL's repeatable read blocks some phantoms. Saying that out loud is a senior signal. Write skew is the one that bites real systems: two transactions each read a valid state, each write, and together they break an invariant no single one violated. It is why on-call scheduling, double-booking and overdraft bugs survive code review.

SOLID learn the failure mode, not the acronym

S
Single responsibility
A module has one reason to change — meaning one stakeholder or actor who can demand a change to it.
When violatedEvery feature touches the same class. Merge conflicts, wide blast radius, no safe refactor.
O
Open / closed
Open for extension, closed for modification. New behavior arrives as new code, not edits to old code.
When violatedAdding one case means editing a switch statement in five files, and you will miss one.
L
Liskov substitution
Any subtype must be usable wherever the base type is expected, without the caller knowing.
When violatedinstanceof checks scattered through callers. The abstraction is a lie and everyone works around it.
I
Interface segregation
No client should be forced to depend on methods it does not use. Many small interfaces beat one large one.
When violatedFat interfaces and stub implementations that throw UnsupportedOperation.
D
Dependency inversion
High-level policy depends on abstractions; details depend on the abstraction too. Wire concretes in at the edge.
When violatedBusiness logic pinned to a vendor SDK. Untestable, and unmigratable when the vendor changes terms.

The senior move on SOLID is knowing when not to apply it. Every one of these buys flexibility by adding indirection, and indirection has a permanent readability cost. Adding an interface for a thing with exactly one implementation and no plausible second one is not good design — it is speculative generality. If an interviewer sees you abstract everything reflexively, that reads as junior, not principled. Say the tradeoff out loud: "I'd keep this concrete until there's a second implementation."

Design patterns that actually appear green = high frequency

Creational
Factory / Abstract factoryhigh
Trigger: object choice depends on runtime input or config. Parsers, payment providers, notification channels.
Builderhigh
Trigger: many optional parameters, or an immutable object assembled in steps. Kills telescoping constructors.
Singletontrap
Trigger: asked about it deliberately. Say it is global mutable state, hostile to testing and to concurrency — prefer a single instance managed by a DI container.
Prototypelow
Trigger: cloning an expensive-to-construct object. Rare in interviews.
Structural
Adapterhigh
Trigger: wrapping a third-party or legacy interface so your core does not depend on it. The practical face of dependency inversion.
Decoratorhigh
Trigger: layering behavior without subclass explosion. Retries, caching, logging, auth around a client.
Facademedium
Trigger: one simple entry point over a messy subsystem. Often the answer to "how do consumers use this?"
Proxymedium
Trigger: lazy loading, access control, or a remote call behind a local-looking interface.
Compositemedium
Trigger: trees where leaves and branches are treated uniformly. File systems, org charts, nested UI.
Flyweightlow
Trigger: millions of near-identical objects sharing intrinsic state. Chess pieces, game tiles.
Behavioral
Strategyhigh
Trigger: interchangeable algorithms selected at runtime. Pricing rules, eviction policies, matching. The most common correct answer in LLD.
Observerhigh
Trigger: one-to-many notification within a process. In-process cousin of pub/sub.
Statehigh
Trigger: behavior changes with lifecycle stage. Orders, vending machines, elevators, ticket reservations.
Commandmedium
Trigger: operations as objects — undo/redo, queueing, audit log, replay.
Chain of responsibilitymedium
Trigger: a request passed along handlers until one takes it. Middleware, validation pipelines, approval flows.
Template methodmedium
Trigger: fixed skeleton, variable steps. Prefer composition over inheritance here when you can.
Iteratorlow
Trigger: traversal without exposing internals. Mostly language-native now.
Visitorlow
Trigger: new operations over a stable type hierarchy. Compilers, AST work.

The LLD round framework 45 minutes, different shape from system design

01
Clarify scope
Which use cases are in, which are explicitly out. Same discipline as system design.
02
Use cases and actors
List the actors and the operations each performs. This produces your interfaces.
03
Core entities
Nouns become classes; verbs become methods. Name the invariants each entity owns.
04
Relationships
Composition over inheritance. Draw the class diagram with cardinalities.
05
Concurrency
What is shared, what is locked, what is immutable. The most-skipped step and the easiest differentiator.
06
Extension
"Now add feature X." A good design absorbs it with new classes, not edits.

What gets people dinged in this round

  • Naming the pattern before naming the problem. "I'll use a factory here" without stating what varies is pattern-matching. Say what varies, then name the pattern that absorbs it.
  • Inheritance where composition belongs. Deep hierarchies are the single most common structural mistake, and they fail Liskov almost immediately.
  • Ignoring concurrency entirely. Most candidates design as if single-threaded. Naming the shared mutable state and how you protect it is a cheap differentiator.
  • Anemic classes. Data holders with getters and setters, and all logic in a service class. That is a database schema wearing an object costume.
  • Over-abstracting a 45-minute problem. Six interfaces for a parking lot is not sophistication. Ship the simple version, then say where you would extend.
  • No invariants. Every entity should own something it refuses to let you break. If nothing is enforced, the design is decoration.
